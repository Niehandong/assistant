## 步骤 0：初始化
1. 拟定需求简称（英文小写短横线，如 `org-management`），目录为 `docs/features/<YYYYMMDD>-<简称>/`（日期取今天），向用户说明。
2. 创建目录和 `input/`，把用户原始描述**原文**保存为 `input/request.md`；用户提供的其他材料也放进 `input/`。
3. Git：工作区不干净时先告知用户并询问如何处理；然后从 `main` 创建分支 `feature/<YYYYMMDD>-<简称>`。

## 步骤 1：产品经理（多轮）
1. 派发 `product-manager`：告知需求目录、原始描述，要求执行第 1 轮。**记住它的 agent ID**，后续轮次用 SendMessage 发回同一个智能体，保留其上下文。
2. 拿到"待确认问题"后，**一次只问用户一个问题**（优先 P0；使用 AskUserQuestion，选项来自问题清单，推荐项放第一个并标注"（推荐）"）。
3. 用户可以随时说"剩下的都按推荐来"，此时把剩余问题全部按推荐答案处理。
4. 把本轮所有回答通过 SendMessage 发回产品经理，要求更新 PRD 并给出新的问题清单。
5. 重复直到产品经理报告"可进入评审检查点"。

### ⛔ 检查点 1：PRD 评审
向用户汇报：PRD 路径、功能点/验收标准摘要、本期不做的范围、仍采用推荐假设的 P1/P2 项。**等待用户明确确认**后才进入下一步。用户提出修改 → 回到产品经理更新。

## 步骤 2：架构师
1. 派发 `architect`：告知需求目录，要求基于 `prd.md` 与现有代码产出 `tech-design.md`。记住 agent ID。
2. 架构师提出 PRD 问题时：属于产品问题 → 先问用户，再交给产品经理更新 PRD，再让架构师继续。

### ⛔ 检查点 2：技术方案评审
向用户汇报：数据模型变更、接口清单（METHOD PATH 权限码）、新增权限码、前后端任务清单、并行安排、风险、新增依赖/中间件。**等待用户明确确认**后才进入开发。

## 步骤 3：开发
1. 按 `tech-design.md` 第 9 节的依赖关系派发：
   - 可并行的任务：在**同一条消息中**同时派发 `backend-dev` 和 `frontend-dev`；
   - 有先后依赖的：先派后端，完成后再派前端。
2. 派发时写清：需求目录、负责的 BE-xx / FE-xx 编号、必须遵守的契约章节。BE 任务按服务分批派发；同一服务的任务不要同时派给两个后端智能体（避免迁移链冲突）；不同服务的任务可并行。
3. 记住两个开发智能体的 agent ID，后续修复用 SendMessage 发回同一个智能体。
4. **契约变更申请**：暂停相关开发 → 交给架构师评估并更新 `tech-design.md` → 若影响 PRD 范围或用户可见行为，先问用户 → 通知受影响的开发按新契约调整。
5. 检查开发返回的"检查结果"，有未通过项不得进入测试，发回修复。

## 步骤 4：测试与修复循环（最多 2 轮修复）
1. 派发 `qa-tester`：告知需求目录，要求按 AC 和多维度测试，输出 `test-report.md`。记住 agent ID。
2. 测试不通过：按缺陷归属分发给 `backend-dev` / `frontend-dev`（SendMessage 到原智能体），附 BUG 编号与报告路径；归属"PRD"的缺陷先问用户；归属"契约"的走契约变更流程。
3. 修复后再派测试做回归（SendMessage 到原测试智能体）。
4. **修复超过 2 轮仍未通过**：停止循环，向用户汇报剩余缺陷，由用户决定（继续修 / 接受遗留 / 调整需求）。

## 步骤 5：交付
1. 向用户汇总：完成的 F-xx、改动文件清单（`git status` / `git diff --stat`）、迁移、新增依赖、测试结论与遗留问题、文档路径。
2. 确认没有测试代码会被提交（`git status` 中不应出现 `backend/tests/`、`frontend/e2e/`、`*.test.ts(x)`）。
3. **等待用户确认后**再提交，提交信息使用 Conventional Commits + 中文描述，例如 `feat(system): 新增组织管理`。
4. 不合并到 `main`、不推送远程，除非用户明确要求。
